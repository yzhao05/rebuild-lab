# Brief interview

Read current-conversation attachments before asking questions. Treat their
exact resolved paths as authorized even when outside the Builder Pack; do not
enumerate their parent directories. Ask only for information not already
present in the supplied documents or specification.
Ask at most three related questions per response.

The reusable-code/source locations are not Gate 1 user input. Read them from
the immutable `LabSpecs/<lab_id>/source-references.json` generated by
`labflow new`, resolve them from the current Builder Pack root, and preserve
the referenced content read-only and unchanged. Ask the user only when the
approved catalog lacks a capability required by the Brief.

Cover:

- stable Lab identity, title, domain, and new/rebuild intent;
- observable learning goals and ordered student tasks;
- formulas, units, sign conventions, assumptions, ranges, invalid input, and
  exact expected results;
- object identity, initial state, allowed actions, feedback, and reset state;
- desktop actions. Automatically record the workflow default that every core
  desktop action has an equivalent XR simulator/controller path with the same
  target, state transition, visible feedback, and success result through the
  Common/XRI adapters. Do not ask the user to design ordinary bindings; ask
  only for a documented/requested semantic exception or when Common cannot
  express the action;
- clean scene layout, mandatory `EMVRRoom/Prefabs/Room_Big_Part_01.prefab`
  placement/adaptation and generated dependency destination, desired visual
  continuity, required approved models,
  camera/XR rig, lighting, UI safe areas, and the mandatory Unity world-space
  readable-front rule (`-Transform.forward` toward the Play Mode camera);
- authored initial visibility, hidden templates/loaders, the first required
  action, and exactly what must become visible after it;
- telemetry order and assist grounding;
- initial, intermediate, completed, reset, error, and lifecycle evidence.

Mark each item `confirmed`, `inferred-needs-confirmation`, or `unresolved`.
Never ask for or locate an old implementation. If a formula or expected result
is absent, ask the user to provide or approve it.

Before confirmation, summarize:

```text
Lab identity
Learning goals
Core student flow
Physics and presets
Objects and feedback
Desktop/XR interactions
Default desktop-to-XR equivalence and confirmed exceptions (normally none)
Clean-scene, mandatory room/XR Setup/XR Simulator Prefabs, camera/UI, and approved-asset plan
Initial state and post-action visible state
Mandatory Common/room/XR reuse audit
Lifecycle, telemetry, and assist
Acceptance evidence
Unresolved items: none
```


## Student manual metadata for future Gate 1

First read confirmed inputs. Ask only for missing `manual_number`, English
`manual_title`, `language`, `report_submission_requirements` and `scoring_policy`.
Use the Brief template's `manual` block and record confirmation. The number is
the course Lab number, never inferred from the Lab ID. At Gate 2 bind exercise
prompts, criterion IDs, points/null, bonus flags and submissions in the rubric's
`manual_assessment`; no inherited 100+5 points, deadlines or Blackboard policy.
See `student-lab-manual.md`. Do not ask these questions during workflow maintenance.
