# Lab 3 Wave Polarization 问题性质分析：技术性失误还是设计性问题

本文对 Lab 3 Wave Polarization 开发过程中出现的问题进行性质归类，区分技术性失误、设计性问题，以及二者混合的问题。

结论先行：

- Lab 3 的主要问题不是物理模型完全错误，而是交互语义和可视化设计不足。
- 技术性失误集中在：误用 batchmode、观察区判定依赖 3D 深度、拖拽命中盒过小。
- 设计性问题集中在：画面对象角色不清、出射光可视化表达不足、预设差异不明显。
- 后续同类 Lab 应优先把“用户能否看懂、能否判断系统识别状态”作为设计约束，而不只是把公式算出来。

## 1. 技术性失误

技术性失误是指需求本身已经明确，但实现时没有遵循已知工程约束、已验证方案或 Unity 交互规律，导致功能或调试流程出现问题。

### 1.1 主动尝试 Unity batchmode

性质：技术性失误。

原因：

- Lab 2 summary 已经明确：本项目不适合由 Codex 主动运行 batchmode 生成或检查。
- 仍然尝试运行 Unity batchmode，重复了之前已归纳的问题。

影响：

- 打断了既定工作流。
- 用户需要手动中止。
- 与“交给用户在 Unity Editor 中生成和反馈”的约定不一致。

最终处理：

- 停止 batchmode。
- 保留 Editor 菜单生成器。
- 后续只根据用户手动生成后的截图/Console 继续修。

后续规则：

```text
Unity 场景生成和编译反馈由用户在 Editor 中执行。
Codex 不主动运行 Unity batchmode，除非用户明确要求。
```

### 1.2 观察区判定依赖 3D Bounds

性质：技术性失误。

原因：

- 在正交相机下，用户的判断基于屏幕投影。
- 初始代码用 3D Bounds/深度判断，导致视觉进入和代码进入不一致。
- Lab 2 已经出现过类似问题：看起来进入透明可视化区，但真实 z 深度不在计算平面。

影响：

- 用户把元件拖进箱子，出射光却不变。
- 用户无法判断是拖拽失败、物理模型没变，还是系统没识别到元件。

最终处理：

- 改为按 `x/y` 屏幕平面判断观察区。
- 状态栏显示实际 active films。

分类理由：

这属于技术实现层面的错误，因为前序 Lab 已经给出了解法：正交视图下避免依赖隐藏深度。

### 1.3 拖拽命中盒过小

性质：技术性失误。

原因：

- 可拖动物体的 collider 与视觉方块接近等大。
- 鼠标射线稍微偏离就无法命中。

影响：

- 用户认为“不能拖动”。
- 交互稳定性差。

最终处理：

```csharp
box.size = new Vector3(1.35f, 1.35f, 0.48f);
```

分类理由：

这是典型交互实现细节问题，可通过 collider 尺寸直接修复。

### 1.4 拖拽灵敏度需要调参

性质：轻微技术性调参。

原因：

- 初始 `dragSensitivity = 2f` 对用户当前视角和场景尺度不够顺手。

最终处理：

```csharp
dragSensitivity = 3f;
```

分类理由：

这不是需求理解错误，而是交互手感参数调整。

## 2. 设计性问题

设计性问题是指代码可能能运行，物理模型也可能计算正确，但用户无法从画面理解对象意义、操作方式或实验现象。

### 2.1 画面对象角色不清

性质：设计性问题。

表现：

- 用户不知道中间箱子有什么用。
- 用户不知道两边蓝色/橘色方块有什么用。
- 用户误以为正弦波可能是可拖动对象。

原因：

- 显示对象和交互对象没有明确区分。
- 标签使用了偏工程化表达。
- 可拖动对象没有明确“drag”提示。

最终处理：

- 中间箱子标为 `Drop films here`。
- 蓝色架标为 `drag blue LP films`。
- 橘色架标为 `drag orange QWP films`。
- 波形标为 `input wave display` / `output wave display`。
- README 明确说明波形不可拖动。

分类理由：

这不是代码 API 错误，而是用户体验和信息架构问题。

### 2.2 文本过多且互相遮挡

性质：设计性问题。

表现：

- 顶部说明、结果、元件标签、预设按钮文字重叠。
- 画面第一眼难以理解。

原因：

- 试图在一个视口内显示太多 handbook 信息。
- 没有把操作说明、物理模型、报告问题、结果显示分层。

最终处理：

- 顶部说明板上移。
- 备用元件架下移。
- 结果面板移动到右上。
- 元件标签缩短为 `LP/QWP`。
- 角度标签缩短为 `axis 45` / `fast 45`。

分类理由：

这是布局和信息密度问题，属于设计性问题。

### 2.3 出射光变化不明显

性质：设计性问题为主，技术实现为辅。

表现：

- 用户按 `1-5` 后觉得出射光变化不明显。

原因：

- 第一版只用黄色正弦波显示输出，偏振态差异被压缩成单一投影。
- 对线偏振、圆偏振、椭圆偏振来说，单条正弦曲线不足以表达核心差异。

最终处理：

- 添加白色 E-field 矢量采样线。
- 右侧偏振轨迹添加即时 E 矢量。
- 给矢量末端加箭头。
- 调整预设，使 `1-5` 默认效果差异更明显。

分类理由：

物理计算可以正确，但可视化选择不足，这是设计性问题；新增矢量采样是技术实现补充。

### 2.4 1-5 预设不够“教学可见”

性质：设计性问题。

表现：

- 预设从 handbook 逻辑上合理，但视觉差异不够强。

原因：

- 预设设计更偏“题目配置”，不够偏“教学演示”。
- 用户按键后希望立刻看到不同现象，而不是必须进一步旋转才能发现。

最终处理：

将预设调整为：

```text
1: LP 45 -> linear, I = 1.00
2: QWP 0 -> circular
3: QWP 0 + LP 90 -> linear, I about 0.5
4: QWP 90 -> opposite circular handedness
5: LP 0 + QWP 30 -> elliptical
```

分类理由：

这是教学交互设计问题，而不是单纯代码 bug。

### 2.5 动画速度过快

性质：设计性调参。

表现：

- 用户要求矢量转速变慢一半。

最终处理：

```csharp
animationSpeed = 1.9f;
```

分类理由：

这是可读性和观察节奏问题，属于交互设计调参。

## 3. 混合型问题

混合型问题同时包含技术实现和设计表达两个层面。

### 3.1 “拖进箱子没变化”

技术层面：

- 观察区判定使用了不适合正交视图的 3D Bounds。

设计层面：

- 用户没有状态反馈，不知道系统是否识别到拖入对象。

最终处理：

- 技术上改用屏幕 `x/y` 判定。
- 设计上增加状态栏：

```text
active films: LP 45, QWP 0 -> LHCP
```

分类结论：

这是混合型问题。只改 Bounds 仍不够，必须同时提供识别反馈。

### 3.2 “两个正弦波都在原地不变”

技术层面：

- 初始波形没有明显动画或差异表达。

设计层面：

- 用户无法区分“波形是显示对象”还是“波形是实验操作对象”。

最终处理：

- 给波形加动画。
- 明确标注 input/output wave display。
- 添加 E-field 矢量和箭头。

分类结论：

这是混合型问题，但根因偏设计：显示方式没有服务于偏振概念。

## 4. 问题分布统计

按本轮 Lab 3 迭代看，问题大致分布为：

```text
技术性失误：
- batchmode 误用
- 3D Bounds 判定
- collider 命中盒过小
- 拖拽灵敏度调参

设计性问题：
- 画面角色不清
- 文本重叠
- 出射光差异不明显
- 预设教学差异不足
- 动画速度过快

混合型问题：
- 拖进箱子但无变化
- 正弦波不动且不可理解
```

总体判断：

```text
Lab 3 的核心失败点更多是设计性问题，而不是物理公式或 Unity API 完全错误。
```

## 5. 后续开发原则

### 5.1 先明确对象角色

每个场景对象都应属于以下类别之一：

```text
可拖动对象
可点击按钮
显示对象
计算区域
说明文本
结果反馈
```

不要让用户猜。

### 5.2 物理可视化必须显示核心差异

对 wave polarization 来说，不能只画一个投影正弦波。

必须同时显示：

- 传播方向波形。
- 横向 E-field 矢量。
- 偏振轨迹。
- 输出分类和相位差。

### 5.3 状态栏必须显示系统识别结果

任何拖拽进入区域、赋值、切换预设类交互，都应有状态栏反馈。

例如：

```text
active films: LP 45, QWP 0 -> LHCP
```

### 5.4 正交相机下不要依赖隐藏深度

用户按屏幕视觉判断是否进入区域，代码也应优先按屏幕平面判定。

这条规则已在 Lab 2 和 Lab 3 中重复验证。

### 5.5 不主动运行 Unity batchmode

除非用户明确要求，否则：

- 不主动运行 Unity batchmode。
- 不把 batchmode 当作默认编译检查方式。
- 由用户在 Unity Editor 中生成场景并提供 Console/Game 反馈。

## 6. 结论

Lab 3 的问题以设计性问题为主，技术性失误为辅。

最重要的教训是：

```text
对于 VR/3D 教学实验，计算正确只是基础；用户必须能一眼看懂对象角色、操作目标、系统识别状态和物理现象差异。
```

Lab 3 后续继续迭代时，应优先围绕以下目标改进：

- 让可拖动对象更明显。
- 让观察区是否生效更明显。
- 让不同偏振态差异更明显。
- 让 handbook 中的 Q1-Q5 与场景预设一一对应且可截图证明。
