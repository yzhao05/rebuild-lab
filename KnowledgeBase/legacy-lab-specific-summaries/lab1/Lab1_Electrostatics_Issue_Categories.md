# Lab 1 Electrostatics 搭建问题归类

本文基于 `Lab1_Electrostatics_Build_Dialogue_Summary.md` 进一步归纳搭建过程中出现的问题。问题分为两大类：

1. 技术型问题：代码、Unity、XR、显示、交互、运行时行为等实现层面的具体问题。
2. 设计/沟通型问题：需求边界、用户信息输入、实验目标表达、测试方式约定等和用户提供信息相关的问题。

## 1. 技术型问题

技术型问题是指即使实验需求已经明确，仍然需要通过代码、场景配置、Unity 设置或运行时调试解决的问题。

### 1.1 Unity 生成流程问题

问题表现：

- 静默 batchmode 生成时间过长。
- 用户无法判断 Unity 卡在生成、编译、加载还是 Play Mode 状态。
- 在 Play Mode 中误触发 Editor 场景生成器，出现 `This cannot be used during play mode` 报错。

改正措施：

- 避免长时间依赖不可见的静默生成。
- 增加生成日志。
- 将任务拆成文档解析、脚本生成、场景生成、Play Mode 测试、问题修正几个阶段。
- 生成器在 Play Mode 中直接拒绝执行，并提示用户先退出 Play Mode。
- 优先使用 Unity Editor 菜单触发场景生成，便于观察。

### 1.2 Unity 场景配置问题

问题表现：

- 场景中出现两个 Audio Listener。
- 桌面相机和 XR 相机同时存在，导致 Unity Console 警告。
- 运行时实际使用的相机和编辑模式观察的 Scene 视图不一致。

改正措施：

- 保证场景中只保留一个有效 Audio Listener。
- 明确 Desktop Preview Camera 和 XR Camera 的职责。
- 在 Play Mode 中固定主要观察相机。
- 避免 XR rig 或预览相机覆盖预期视角。

### 1.3 代码 API 使用问题

问题表现：

- 编辑模式下访问 `renderer.material`，触发材质实例化 warning。
- Play Mode 中调用 Editor-only API。
- 拖动刚体时设置 kinematic rigidbody 的 velocity，可能触发 warning。

改正措施：

- 编辑模式材质读取改用 `sharedMaterial`。
- 动态颜色改用 `MaterialPropertyBlock`。
- Editor 生成逻辑只在非 Play Mode 下运行。
- 拖动物体时区分刚体是否为 kinematic，避免设置不合适的物理属性。

### 1.4 文本显示问题

问题表现：

- 初始生成的文字过大。
- 多块文字严重重叠。
- Play Mode 下文字左右镜像。
- 悬停提示文字方向错误。
- 部分文字和 hover 注释分辨率低、看不清。

改正措施：

- 缩小 TextMesh 字体并重新布置面板。
- 将信息拆分成 Workflow、Report、Models 三个区域。
- 调整文字与背景板间距，提高对比度。
- 统一文本朝向，使文字面向运行时主摄像机。
- 区分编辑模式 Scene 视角和 Play Mode Game 摄像机视角。
- 调整摄像机距离和文字缩放，降低采样模糊。

### 1.5 摄像机与视角问题

问题表现：

- 场景斜对镜头，用户难以观察。
- 改动后出现镜像文字。
- 编辑模式中文字正常，Play Mode 后文字反向。

改正措施：

- 将场景改为正对镜头。
- 固定 Play Mode 主摄像机位置。
- 避免同时翻转摄像机和文字方向导致互相抵消。
- 最终以 Game 视图的实际运行效果为准。

### 1.6 XR 与桌面测试问题

问题表现：

- XR Device Simulator 面板过大，遮挡实验场景。
- 手柄射线不可见。
- XR 插件虽然已搭载，但默认交互没有达到实验需要。
- 没有头显时难以测试 VR 交互。

改正措施：

- 隐藏或缩小 XR Device Simulator UI。
- 增加 XR fallback ray，使手柄射线在默认线渲染异常时仍可见。
- 保留桌面鼠标模拟 VR 手柄的测试模式。
- 使用鼠标移动表示指针方向，鼠标左键按住表示抓取/拖动。
- 让 VR 与桌面测试共享同一套拖动接口。

### 1.7 鼠标/手柄交互问题

问题表现：

- 1-5 中只有部分按钮响应。
- 下方按钮 hover 提示方向错误。
- 透明 Field Cube 可能挡住鼠标射线，导致后方物体选不中。
- 只有 1、2、5 按钮能被拖动或重点测试。

改正措施：

- 修正 1-5 数字键与预设按钮的绑定。
- 为按钮加入 `ElectrostaticPresetPad` 交互逻辑。
- 鼠标射线改用 `Physics.RaycastAll`，选择最近的可拖拽物体。
- 抽象 `IEmVrMouseDraggable` 接口。
- 将 1、2、5 号按钮高亮，使用户知道重点交互对象。

### 1.8 充电与物理行为问题

问题表现：

- 充电区看起来没有反应。
- 拖动物体进入红/蓝区域时没有明显电荷变化。
- 用户不清楚哪些对象是电荷，哪些对象只是充电器。

改正措施：

- 红色区域赋予正电。
- 蓝色区域赋予负电。
- 拖动物体进入充电区时立即充电。
- 增加距离 fallback，不完全依赖 trigger 碰撞。
- 通过颜色、标签和说明区明确电荷、充电器、预设场景的区别。

### 1.9 场景尺度问题

问题表现：

- 初始场景太紧凑。
- 文字、按钮、电场可视化区域相互挤压。
- 需要更大的实验空间。

改正措施：

- 将场景长宽高扩大两倍。
- 同步调整摄像机距离。
- 增加按钮、提示板、实验对象之间的间距。
- 保证扩大场景后 Game 视图仍能完整看到实验主体。

### 1.10 代码结构问题

问题表现：

- Lab 1 初期代码混在一起。
- 后续 Lab 2、Lab 3 需要复用交互、hover、XR 射线等逻辑。
- 如果不拆分，多个实验会出现重复代码。

改正措施：

- 新建公共代码目录：
  - `Assets/Scripts/Common/`
- 新建 Lab 1 专用目录：
  - `Assets/Scripts/Lab1_Electrostatics/`
- 新建 Lab 2、Lab 3 目录：
  - `Assets/Scripts/Lab2_Magnetostatics/`
  - `Assets/Scripts/Lab3_WavePolarization/`
- 将公共能力和 Lab 1 专有物理逻辑分离。
- 保留 `.meta` 文件，降低 Unity 引用丢失风险。

## 2. 设计/沟通型问题

设计/沟通型问题主要和用户输入信息、实验目标描述、测试方式约定有关。这类问题不一定是代码错误，但会影响实现方向、工作效率和最终体验。

### 2.1 初始需求范围较大

问题表现：

- 用户最初要求“从头构建 Unity 物理 3D Lab 并完成实验”。
- 该需求同时包含文档理解、物理建模、Unity 场景、交互、VR 支持、可视化、测试说明等多个层面。

影响：

- 如果不拆阶段，容易出现一次性生成过大、调试困难、等待时间过长的问题。
- 用户很难判断当前进度卡在文档解析、代码生成、Unity 编译还是场景运行。

改进建议：

- 今后类似任务建议先明确阶段：
  - 先读实验文档。
  - 再出场景设计说明。
  - 再生成最小可运行版本。
  - 再补充 VR 操作。
  - 最后优化显示和交互。

### 2.2 初始未明确 Unity 运行环境

问题表现：

- 一开始需要确认 Unity 安装路径。
- 后来用户补充 Unity 在 `E:\unity\2022\Editor\Unity.exe`。
- 当前已有 Unity 进程在运行，这会影响 batchmode 或项目锁。

影响：

- 如果不知道 Unity 路径，无法自动调用 Editor。
- 如果已有 Editor 运行，后台 batchmode 可能失败或卡住。

改进建议：

- 用户应提前提供：
  - Unity 版本。
  - Unity Editor 路径。
  - 是否已有 Editor 打开。
  - 项目是否正在编译。
  - 是否允许 batchmode。

### 2.3 初始未明确是否以 VR 为主

问题表现：

- 初期按 3D/桌面可运行 Lab 设计。
- 后续用户明确指出这是 VR Lab，XR 插件已经搭载好。
- 需要将操作改成 VR 手柄操作。

影响：

- 早期交互逻辑偏向键盘/鼠标。
- 后续需要补充 XR 手柄射线、VR 抓取、hover、select 等交互。

改进建议：

- 开始搭建前应明确：
  - 是否必须支持真实 VR 设备。
  - 是否需要支持 XR Device Simulator。
  - 是否保留桌面鼠标测试。
  - 鼠标如何映射到手柄操作。

### 2.4 初始未明确测试方式

问题表现：

- 用户后来说明：当前测试用鼠标代表手柄，按住鼠标左键代表拖动。
- 这个约定不是一开始就明确的。

影响：

- 初期实现的鼠标测试和用户预期不完全一致。
- 需要后续修改鼠标指针、拖动、充电触发逻辑。

改进建议：

- 用户应提前说明测试输入设备：
  - 真实 VR 手柄。
  - XR Device Simulator。
  - 鼠标键盘。
- 如果用鼠标模拟 VR，应明确：
  - 鼠标移动代表什么。
  - 左键/右键代表什么。
  - 是否需要拖拽、点击、悬停、长按。

### 2.5 初始未明确视觉优先级

问题表现：

- 初始生成了很多实验说明文字。
- 用户运行后发现文字过大、重叠、看不清。
- 后续多次围绕字体大小、清晰度、朝向和布局调整。

影响：

- 说明内容完整，但第一版视觉拥挤。
- 需要根据用户截图反复调节。

改进建议：

- 开始前应明确：
  - 场景中是否需要完整显示实验手册内容。
  - 文字是给桌面屏幕看，还是给 VR 头显看。
  - 优先显示中文、英文，还是只显示简短英文标签。
  - 一屏内最多显示多少说明文字。

### 2.6 初始未明确哪些对象必须可交互

问题表现：

- 用户后续反馈只有 1、2、5 可以拖动，要求把 1、2、5 标红突出。
- 用户询问“电荷在哪里”，说明对象角色不够直观。

影响：

- 用户不容易区分：
  - 电荷。
  - 充电区。
  - 预设按钮。
  - 实验观察对象。
  - 只是装饰或说明的对象。

改进建议：

- 场景设计前应列出对象清单：
  - 哪些对象可拖动。
  - 哪些对象可点击。
  - 哪些对象只用于显示。
  - 哪些对象会改变电荷状态。
  - 哪些对象用于切换实验问题。

### 2.7 用户截图是关键反馈来源

问题表现：

- 很多问题只有通过截图才能发现：
  - 文字镜像。
  - 字体重叠。
  - Device Simulator 遮挡。
  - Console warning。
  - Game 视图和 Scene 视图不一致。

影响：

- 没有截图时，只靠代码推断容易误判视觉问题。
- Unity 场景任务必须结合实际运行画面迭代。

改进建议：

- 每次重大修改后，用户最好提供：
  - Game 视图截图。
  - Scene 视图截图。
  - Console 截图。
  - 当前是否处于 Play Mode。

### 2.8 实验文档和最终交互之间需要转译

问题表现：

- PDF 手册描述的是实验内容和问题。
- Unity 场景需要将这些内容转译成对象、按钮、提示、交互和可视化。

影响：

- 文档中的每个问题不一定都适合原样显示在场景中。
- 需要决定哪些内容做成按钮，哪些内容做成模型，哪些内容做成说明文字。

改进建议：

- 用户可提前指定：
  - 哪些实验问题必须完整实现。
  - 哪些问题只需要文字提示。
  - 哪些公式必须显示。
  - 是否需要生成实验报告截图点位。

### 2.9 多 Lab 规划应提前考虑

问题表现：

- Lab 1 先实现，后面才加入 Lab 2、Lab 3 的共性代码整理需求。
- 因此需要后期移动文件、拆分目录。

影响：

- 如果一开始只按 Lab 1 写，后续扩展到多个 Lab 会产生重构成本。

改进建议：

- 如果目标是一组 VR Labs，应在第一个 Lab 开始时就规划：
  - `Common` 公共代码。
  - 每个 Lab 的专属目录。
  - 统一的交互接口。
  - 统一的 README 模板。
  - 统一的场景生成器命名规则。

## 3. 简要结论

本次搭建中，技术型问题主要集中在 Unity 运行机制、XR 交互、摄像机视角、文字显示、物理交互和代码结构上。

设计/沟通型问题主要集中在初始需求范围较大、VR 操作方式未一开始明确、测试设备和鼠标模拟规则后置、可交互对象和视觉优先级需要通过截图反复确认。

后续搭建 Lab 2、Lab 3 时，建议先完成以下确认：

- 该 Lab 的核心物理对象是什么。
- 哪些对象可抓取、可旋转、可点击。
- 是否必须支持真实 VR 手柄。
- 桌面鼠标如何模拟 VR 操作。
- 一屏内需要显示哪些文字。
- 是否先做最小可运行场景，再逐步增加说明和报告任务。
